# 08｜开发执行、任务领取与 PR 手册

## 1. 一次工作的输入包

必须有任务 ID、所属模块、前置任务或已冻结契约、批准目标、修改目录、输入版本、验收、测试命令及不允许做的事。现在没有真实开发成员安排，因此 Owner 字段使用前端/后端/执行/质量/安全等职责，领取时再绑定人。

任务索引的 180 个工作包均为 Planned。选择 Ready 工作前验证依赖和实际代码，不以文件顺序假定依赖已完成。共享契约允许并行使用 Fixture，但必须标出待联调，不能用 Fixture 通过真实基座验收。

## 2. 执行流程

1. 领取一项任务并检查仓库；在 Issue 或计划记录绑定实际负责人、目标分支与依赖。
2. 阅读模块计划和公共契约。若发现冲突，先提交 ADR/需求变更草案，不让不同模型各猜一套。
3. 用单独分支与工作区实施，补齐测试。需要多个 Agent 时按独立边界分工，指定共享契约 owner。
4. 提交 PR，包含任务 ID、范围、测试、截图/契约差异、迁移和风险。只有真实运行过的测试可以标通过。
5. 评审者检验验收证据；安全、权限、迁移、发布及跨模块契约有对应专业复核。
6. 合并后更新任务状态和证据链接，业务完成与部署/发布状态仍分开。

## 3. 状态

Planned → Ready → InProgress → InReview → Done。Blocked、NeedsDecision 是独立标志。部分完成时保存实际交付和未完成清单，不把整项标 Done。废弃任务保留替代任务与决定，不能删除来美化进度。

## 4. 分支与提交

建议 `feat/ZT17-02-studio-shell`、`fix/ZT15-03-lease-fencing`、`docs/...`；这是团队约定提案。每 PR 应可独立理解和回退，提交 message 描述实际行为，不使用“全部完成”掩盖范围。不能擅自强推共享分支。

## 5. 多 Agent 并行约定

由人确认公共 contracts、migration 和 shared UI 负责人。不同模型分别改不同包，跨包改动先协调。一个任务可以多个 Run，每个 Run 有自己的产物和验证；无需把所有内部对话合并成一段历史。

审查 Agent 可以提供独立意见，但不能代替必须的人类或政策批准。禁止削弱测试、使用生产密钥、上传客户内容、私自增加供应商或超出预算。

## 6. 示例领取包

任务 `ZT17-02`：实现 Studio 独立路由与工作区恢复；读取 ZT17、公共 API 和 Workspace/Run 区别；只修改 apps/studio 与 client 的相关接口；覆盖首次打开、刷新、多窗口、权限撤回和不存在工作区；验收要求 GET 不启动 Run，恢复不重复执行。

这只是任务边界示范，实际步骤以对应模块文档为准。不存在的命令先实施并评审，不向用户声称已运行。

## 7. 工作估算与排期

采用实际吞吐、评审能力和依赖确定日期。不预设 AI 比人快多少；模型费用和人工纠错都进入成本。完成首批后用区间估算，不把故事点或文档行数直接换算天数。

## 8. 本次不自动做的事

本计划不会替用户创建 180 个真实 Issue、分配人员、通知团队、配置计费、调用真实模型或部署系统。提供机器可读索引和模板，后续由明确操作把相应任务导入 GitHub。PR 合并仍由仓库负责人决定。
